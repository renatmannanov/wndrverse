# Шаг 7: Калибровка качества кластеров (главный приоритет)

> Зависит от: шаг 6 (рабочий end-to-end)
> Статус: [ ] pending

## Задача

Это НЕ кодовый шаг, а эмпирическая калибровка порогов на реальных данных. Цель —
чтобы в темах НЕ было флуда/коротких фраз/неподходящих сообщений (главное
требование заказчика). По итогу — зафиксировать дефолтные пороги в `topics.py`.

Известный риск: HDBSCAN на узком срезе (неделя одного топика = 20–50 сообщений)
может унести почти всё в noise (-1) → мало/ноль тем. Здесь это проверяем и
подбираем.

## Что делать

1. **Прогнать на трёх срезах** boltalka (самый разговорный, 3668 сообщений):
   - `--period 1w` (узкий — стресс-тест на noise),
   - `--period 1m` (рабочий),
   - `--period all` (широкий — стресс-тест на слипание тем).
   ⚠️ `--period all` на boltalka — это UMAP+HDBSCAN на ~тысячах векторов 1536-dim,
   может считаться минуты и съесть память. Гонять РЕДКО, не в цикле подбора. Для
   итеративной калибровки порогов использовать `1m` (быстрее), `all` — финальная
   проверка на слипание.
2. **Глазами оценить** каждый вывод по чек-листу:
   - нет ли в темах коротких фраз / «ахаха» / «+» / односложного флуда;
   - названия тем осмысленны и различимы (не «общение», «разное» на всё);
   - ссылки кликабельны и ведут в релевантное место (открыть 3-4 ссылки руками);
   - число сообщений в теме правдоподобно;
   - порядок тем соответствует ощущению «горячести».
3. **Подобрать пороги** (крутить дефолты в `build_topics`):
   - если много флуда в темах → поднять `min_chars` (80→120/150) и/или ужесточить
     `_is_substantive`;
   - если на 1w почти всё в noise → снизить `min_cluster_size` (3→2) для узких
     периодов; зафиксировать как дефолт, если не ломает 1m/all;
   - если темы слипаются в одну огромную → поднять `min_cluster_size` или
     `min_samples`;
   - если рыхлые хвосты в темах → поднять `min_probability`.
4. **Зафиксировать** финальные дефолты в `topics.py` с комментарием, ОТКУДА
   значения (по аналогии с комментарием про A/B/C-тест в synthesis.py).

Правило #1: финальные пороги — ОДИН набор дефолтов в коде, не «подбирай каждый
раз». Если для узких vs широких периодов нужны разные — сделать это
детерминированным внутри `build_topics` (например min_cluster_size зависит от
len(fragments) по явному порогу), а не оставлять на усмотрение.

## Команды для верификации

```bash
python -m delivery topics --topic boltalka --period 1w
python -m delivery topics --topic boltalka --period 1m
python -m delivery topics --topic boltalka --period all
# Спот-чек на другом разговорном топике
python -m delivery topics --topic requests --period all
```

## Критерии готовности

- [ ] На boltalka 1m: ≥3 осмысленные различимые темы без флуда в них.
- [ ] На boltalka 1w: не пустой результат (noise не съел всё) ИЛИ осознанное
      решение, что узкий период даёт мало тем — задокументировано.
- [ ] Открыты руками ≥3 ссылки — ведут в реальные релевантные сообщения.
- [ ] Финальные пороги зафиксированы в `topics.py` с комментарием-обоснованием.
- [ ] Записать вывод калибровки в progress.md (какие пороги, почему).
