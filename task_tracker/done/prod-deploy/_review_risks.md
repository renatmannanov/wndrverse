## Критичное (только [CONFIRMED] и [LIKELY])

### 1. `*.sql` НЕТ в `.gitignore` — дамп с PII может попасть в git [CONFIRMED]

**Шаг:** step_1, п.5; PLAN.md решение 2; .gitignore.  
**Что не так:** step_1 говорит «Дамп-файл НЕ коммитить (gitignore `*.sql`)». step_5 проверяет `git check-ignore .env core/ingest/topic_map.json` — но `*.sql` там нет. При проверке `.gitignore` в репо обнаружено: паттерна `*.sql` нет совсем. Дамп `wndrverse_corpus.sql` будет создан в `~/claude-hub/projects/wndrverse/` на VPS и локально — и при `git add .` или небрежном `git add` попадёт в индекс вместе с PII (author_name реальных участников).  
**Опасность:** PII утечёт в публичный git-репозиторий `renatmannanov/wndrverse` (по deploy-карте CLAUDE.md репо публичный).  
**Фикс (до step_1):** добавить `*.sql` в `.gitignore` в корне репо.

### 2. `core.db init` перед restore в уже непустую БД — риск конфликта схемы [CONFIRMED]

**Шаг:** step_1, п.4 и п.5.  
**Что не так:** step_1 предписывает: сначала `core.db init` (создаёт схему), затем `cat wndrverse_corpus.sql | docker compose exec -T db psql`. Если дамп сделан с DDL (а pg_dump по умолчанию включает DDL — CREATE TABLE, индексы, pgvector extension), то restore попытается создать уже существующие таблицы и завершится с ошибками. Исполнитель может не заметить ошибки в потоке и считать restore успешным (count совпал частично или вообще не совпал).  
**Опасность:** молчаливо неполный корпус на проде; dup_keys или частичные данные.  
**Фикс:** либо делать `core.db init` только если дамп без DDL (--data-only), либо пропустить `init` и положиться на DDL из дампа, либо явно задокументировать флаги pg_dump.

### 3. Restore в непустую БД без явной очистки — задвоение если step переделывается [LIKELY]

**Шаг:** step_1, п.5.  
**Что не так:** если step_1 выполняется повторно (после ошибки, или перезапуск), схема уже есть и данные могут быть частичные. `cat dump | psql` без `--clean` или предварительного DROP не очистит старые данные — INSERT натолкнётся на конфликты по `external_id` (unique key), часть вставок упадёт, часть пройдёт. Тест «dup=0» может пройти (если ключ уникален) но `total` не совпадёт с локальным.  
**Опасность:** невоспроизводимый результат при повторном прогоне; трудно диагностировать.  
**Фикс:** перед restore либо `DROP DATABASE / CREATE DATABASE`, либо `pg_restore --clean`, либо явная проверка «БД пустая?» как предусловие.

### 4. chat_id в `progress.md` записан открытым текстом и файл в git [LIKELY]

**Шаг:** progress.md (строка «chat_id = -1002924475859. thread 16139 → questions_to_women...»); PLAN.md решение 7 («значения в план/git НЕ писать»).  
**Что не так:** решение 7 явно запрещает писать значения секретов в план/git. `progress.md` — файл плана, лежит в `task_tracker/todo/prod-deploy/` который в git. В нём записаны реальный chat_id и thread_id WNDR-группы. Это не токен и не ключ, но противоречит правилу и может раскрыть ID приватной группы публично.  
**Опасность:** раскрытие ID закрытой WNDR-группы в публичном репозитории. Средний риск (не ключ API), но нарушение явного правила.  
**Фикс:** перенести эти значения в gitignored файл (topic_map.json или отдельный notes.local.md), удалить из progress.md.

## Важное (только [CONFIRMED] и [LIKELY])

### 5. Порт 5434 на VPS — проверка упомянута, но процедуры fallback нет [CONFIRMED]

**Шаг:** step_1, п.4: «Порт 5434 на VPS — проверить, что свободен (не занят ayda/другим). Если занят — поменять маппинг в docker-compose.yml ТОЛЬКО на VPS».  
**Что не так:** план предлагает поменять маппинг «только на VPS», но docker-compose.yml один — он в git. Изменение только на VPS создаёт расхождение между репо и проводом: следующий `git pull` перезапишет правку. Никакого `docker-compose.override.yml` не упомянуто.  
**Опасность:** при следующем git pull порт-маппинг вернётся в 5434, что сломает уже работающую БД или конфликт с ayda/другим сервисом.

### 6. `OnCalendar=Asia/Almaty` — systemd может не поддерживать named timezone [LIKELY]

**Шаг:** step_3, п.1 и п.2.  
**Что не так:** systemd поддерживает named timezones в OnCalendar начиная с v247 (Ubuntu 20.04 = v245 — НЕ поддерживает; Ubuntu 22.04 = v249 — поддерживает; Ubuntu 24.04 = ok). VPS — Ubuntu 24.04 (указано в CLAUDE.md), должно работать. Но таймзона сервера влияет на интерпретацию: если `TZ` системы уже установлен иначе — результат может быть не тот. Это LIKELY, не CONFIRMED: Ubuntu 24.04 должен справиться, но верификация в плане не упомянута.  
**Фикс:** добавить проверку `systemd-analyze calendar "*-*-* 09:00:00 Asia/Almaty"` как шаг верификации в step_3.

---

### 7. `systemctl start wndr-digest.service` в step_4 — реальная трата OpenAI без стоп-точки на «уже запускался» [CONFIRMED]

**Шаг:** step_4, п.1 и «⚠️ СТОП-ТОЧКА».  
**Что не так:** стоп-точка проверяет наличие данных (`< 3 фрагментов`), но не проверяет, не запускался ли уже синтез (artifact для этого топика уже есть в artifacts таблице). Повторный запуск `systemctl start wndr-digest.service` при уже существующем артефакте приведёт к повторной трате на синтез Pass1+Pass2. Нет проверки «artifact уже есть → не гони заново».  
**Опасность:** двойная трата при отладке step_4 (реальный OpenAI синтез).

### 8. `sudo systemctl enable --now` — sudo у rm_agent на продакшен VPS [LIKELY]

**Шаг:** step_2, п.2; step_3, п.3.  
**Что не так:** plan использует `sudo systemctl` для создания юнитов в `/etc/systemd/system/`. Права `sudo` у пользователя `rm_agent` не верифицированы в плане (только предполагаются). Если `rm_agent` не в sudoers или sudoers настроен restrictively (NOPASSWD только для конкретных команд), — эти шаги упадут. Нет шага предварительной проверки `sudo -l`.  
**Опасность:** план упирается на шаге 2 без диагностики почему.

---

### 9. `EnvironmentFile` в systemd-юнитах — опечатка или несуществующий путь не даёт ошибку старта [CONFIRMED]

**Шаг:** step_2, п.1; step_3, п.1 и п.2.  
**Что не так:** все юниты используют `EnvironmentFile=/home/rm_agent/claude-hub/projects/wndrverse/.env`. Если каталог на VPS выбран другой (step_1 оставляет открытым вопрос — `~/claude-hub/projects/wndrverse` или `~/claude-hub/projects/wndrverse-core`), путь в юните будет неверным. systemd при неверном `EnvironmentFile` (без `EnvironmentFile=-`) не запустит сервис с ошибкой `No such file or directory`, и journalctl покажет это только после `enable --now`.  
**Опасность:** бот и таймеры не запустятся; диагностика неочевидна если путь менялся.  
**Фикс:** сначала зафиксировать каталог в step_1, затем жёстко вписать в юниты; или использовать `EnvironmentFile=-` (тире = не падать если нет файла — но тогда секреты просто не загрузятся молча).

### 10. Дамп передаётся через `scp` без шифрования-at-rest на промежуточном этапе [CONFIRMED]

**Шаг:** step_1, п.5.  
**Что не так:** `wndrverse_corpus.sql` создаётся локально (в рабочей папке проекта), копируется scp, лежит на VPS в `~/claude-hub/projects/wndrverse/`. После restore план не предписывает удалить файл дампа с VPS. `step_5.md` проверяет только «не в git», не «удалён с диска».  
**Опасность:** файл с PII (author_name тысяч сообщений) остаётся на VPS бессрочно в открытом тексте, доступен всем с доступом к rm_agent.  
**Фикс:** добавить в step_5 чеклист: «дамп удалён с VPS и локально после верификации».

## Мелочи ([THEORETICAL])

### T1. Имена systemd-юнитов `wndr-*` — конфликт с OpenClaw/Hermes

Теоретически возможен если OpenClaw/Hermes тоже используют префикс `wndr-`. Ни CLAUDE.md, ни план не описывают юниты соседних проектов. Проверить: `systemctl list-units | grep wndr` на VPS.

### T2. `docker compose project name` конфликтует с другим compose на VPS

По умолчанию project name = имя папки (`wndrverse`). Если ayda или другой проект в папке с тем же именем — конфликт сети/volume. Теоретично; проверить `docker compose ls` на VPS.

### T3. `digest.scheduler` — модульный путь не совпадает с кодом

step_3 вызывает `python -m digest.scheduler --now`. В CLAUDE.md упомянут `delivery/` (не `digest/`). Может быть расхождение в имени модуля. Теоретично — требует проверки кода, а не плана.
