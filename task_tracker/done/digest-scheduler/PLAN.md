> Статус: done

## Цель

Обвязать уже работающее ядро дайджеста (`delivery digest` → `core/brain/synthesis`)
расписанием и доставкой в Telegram-личку. Скрипт раз в день синтезирует дайджест по
топикам WNDR chat и шлёт его пользователю в ЛС через бота-ингестора. Ядро синтеза НЕ
переписываем — только добавляем (а) telegram-канал доставки, (б) ограничение длины,
(в) topic-хинты под новые топики, (г) планировщик-процесс.

## Ключевые решения (зафиксированы, не обсуждаются в ходе работы)

1. **Источник.** WNDR chat `chat_id = -1002924475859`, форум-топики:
   - `thread_id 16139` → «Вопросы к Женскому миру» → ключ `questions_to_women`
   - `thread_id 16138` → «Вопросы к Мужскому миру» → ключ `questions_to_men`
   Вносятся в `core/ingest/topic_map.json` (он gitignored). Бот-ингестор должен
   быть в этой группе и пособирать сообщения ДО осмысленного дайджеста.
2. **Доставка — в личку.** `user_id = 423915315`. Канал `telegram_dm` в
   `delivery/channels.py` (сейчас там `NotImplementedError` — extension point готов).
   Шлёт **тот же бот** `BOT_TOKEN_INGEST`. Пользователь обязан раз написать боту
   `/start` (Telegram не даёт боту писать первым).
3. **Планировщик — sleep-loop на stdlib.** APScheduler НЕ ставим (нет в окружении,
   не тащим зависимость). Процесс `digest/scheduler.py`: считает время до следующего
   запуска в таймзоне `Asia/Almaty`, спит, дёргает синтез+доставку, повторяет.
4. **Таймзона — явная, через `zoneinfo` + ENV `WNDR_DIGEST_TZ` (дефолт `Asia/Almaty`).**
   Время запуска — ENV `WNDR_DIGEST_AT` (дефолт `09:00`). Прицел на VPS (там TZ=UTC):
   расписание привязано к именованной зоне, не к локальному времени машины — при
   переезде момент отправки не сдвигается.
5. **Период — `1d`** (сообщения за сутки), частота — раз в день. Оба через ENV
   (`WNDR_DIGEST_PERIOD` дефолт `1d`).
6. **Длина — два слоя.** (а) Промпт `digest_synthesis.md` просит модель уложиться в
   ~3500–4000 символов; `complete()` зовётся с `max_tokens` как потолок. (б)
   Страховочная обрезка до 4096 в `channels.py` (telegram_dm) с `logger.warning`,
   если модель всё же превысила. Telegram режет на 4096 — без страховки бот упал бы.
7. **Стоп-точка на деньгах.** Перед первым реальным синтезом — `--estimate`
   (см. step). enrich на новых WNDR-данных тратит OpenAI.
8. **PII не ломаем.** В OpenAI уходит только `[#id]` + текст; имена подставляются
   локально в `humanize_refs`. Доставка работает с уже humanized-текстом — поведение
   не меняем.
9. **Ядро не трогаем по сути.** `synthesize()` / `_run_digest()` остаются. Длину
   добавляем как параметр промпта + max_tokens, не переписывая two-pass логику.

## Что НЕ в этом MVP (защита от scope creep)

- ❌ Доставка в топик группы (только ЛС пользователю).
- ❌ `--angle` (уточнение угла) — только не мешать: сигнатуры синтеза принимают
  свободный topic_hint, новый аргумент допишется позже без переделки.
- ❌ Триггер по накоплению контекста — в бэклог (`task_tracker/backlog/`).
- ❌ APScheduler / cron / systemd — sleep-loop на stdlib; деплой на VPS = отдельная
  задача, отдельное окно.
- ❌ Нарезка длинного дайджеста на несколько сообщений — пока обрезка до 4096.
- ❌ Правка two-pass логики synthesis, схемы БД, curator/, agent-template/.
- ❌ Восстановление пропущенного запуска (V5): если процесс упал и поднялся ПОСЛЕ
  целевого времени — `_seconds_until_next` назначит следующий запуск на завтра,
  пропущенный дайджест НЕ догоняется. Осознанное решение для MVP (sleep-loop без
  персистентного состояния «когда был последний запуск»).
