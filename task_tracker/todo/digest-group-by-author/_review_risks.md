# Review: Risks — digest-group-by-author

> Дата: 2026-06-04. Источники: PLAN.md, step_1..4.md, progress.md, CLAUDE.md.
> Категории: [CONFIRMED] = найдено в тексте плана; [LIKELY] = обоснованное предположение; [THEORETICAL] = не включаются в Критичное/Важное.

---

## Критичное (только [CONFIRMED] и [LIKELY])

### 1. PII-утечка через `author_name` в аноним-ветке — [CONFIRMED]

**Шаг 1, функция `_group_by_author`, строки в step_1_group_and_refs.md:**

```python
name = f.get('author_name') or 'аноним'
if f.get('sender_id') is None and not f.get('author_name'):
    name = 'аноним'
by_key[k] = {'name': name, 'texts': []}
```

Ветка `('name', f['author_name'])` (sender_id=None, author_name есть) попадает в `by_key` с ключом `('name', <реальное_имя>)`. Сам ключ — это `author_name` буквально. Ключ используется только внутри, имя хранится в `by_key[k]['name']` — в `grouped_text` напрямую не попадает. **Но** тест в step_1 гласит: `assert name not in text` — это проверка для `grouped_text`. Ключ `by_key` сам по себе не попадает в LLM. Риск снят для `grouped_text`.

**ОДНАКО** — `author_refs[n] = by_key[k]['name']` — и `author_refs` уходит как часть возврата из `synthesize()`. `synthesize_and_save` должен пробросить его в `build_digest`, который передаёт в `humanize_author_refs`. Если где-то `author_refs` залоггируется в `journalctl` (например, `logger.debug(result)` в `synthesize_and_save`), реальные имена окажутся в логах на VPS. **В плане нет инструкции проверить logging-уровень в synthesis.py/synthesize_and_save.** [CONFIRMED — пункт про проверку логов отсутствует в критериях готовности step 1 и step 3]

---

### 2. Анонимный `sender_id=None, author_name=None` → каждое сообщение = отдельный автор — [CONFIRMED]

**Шаг 1, `_author_key`:**

```python
return ('anon', f['id'])  # each anon message its own "author"
```

Это задокументированное поведение — каждое анонимное сообщение получает свой `[@N]`. При 10 анонимных сообщениях в диапазоне получим `[@5] [@6] [@7] ... [@14]` — по одной строке на каждое. Блок «КТО ЧТО» раздуется. Промпт в шаге 2 говорит «ОДИН участник» для `[@N]`, но LLM не знает что `[@5]..[@14]` — это анонимы-одиночки, не группы. Визуально в выводе пользователь увидит 10 строк с разными `[@N]` вместо понятного «аноним ×10». **Нет ни одного теста или критерия для кейса «много анонимов»** — только один кейс `sender_id=None, author_name=None → 'аноним'` для одного фрагмента. [CONFIRMED — step_1 тесты покрывают единственный аноним, множественные не упомянуты]

---

### 3. LLM выдумывает `[@N]` которого нет во входе — план не покрывает — [LIKELY]

Промпт в шаге 2 запрещает «придумывать номера»: *«НЕ придумывай номера. Имя подставит система.»* Но нет механизма валидации: `humanize_author_refs` при неизвестном N оставляет `[@N]` as-is (step_1: *«Unknown N left as-is»*). Если LLM напишет `[@7]`, которого нет в `author_refs`, в выводе останется сырой `[@7]` — пользователь увидит нерасшифрованную ссылку. В критериях готовности step_1 только `pytest` и глазная проверка на одном прогоне — систематической проверки «нет лишних `[@N]` в выводе» нет. [LIKELY: поведение `humanize_author_refs` при неизвестном N явно описано в плане; риск выдумывания у LLM общеизвестен]

## Важное (только [CONFIRMED] и [LIKELY])

### 4. Слияние в master без прохождения git-стратегии через dev — [CONFIRMED]

**Шаг 3, step_3_deploy_and_smoke.md:**

```bash
git checkout master && git merge --no-ff feature/digest-group-by-author ...
git push origin master
```

CLAUDE.md (глобальный, Git-стратегия) требует: `feature/* → dev (тест) → main`. Шаг 3 сливает напрямую в `master`, минуя `dev`. Это нарушение зафиксированной стратегии. Для данного проекта ветка `dev` не упоминается в CLAUDE.md wndrverse — есть только `master`. Потенциально ок, но агент-исполнитель, читающий глобальный CLAUDE.md, может запутаться. [CONFIRMED — шаг 3 явно пишет `git merge ... master`; глобальный CLAUDE.md требует `feature → dev → main`]

### 5. Отсутствие стоп-точки перед `git push origin master` — [CONFIRMED]

**Шаг 3:** `git push origin master` идёт в одном блоке с merge, без явного «СТОП — подтверди у владельца». Стоп-точка есть только для прод-smoke (`/summary`), но не для самого push на master. Если агент выполняет шаг 3 автономно, он запушит в прод без явного ок. CLAUDE.md wndrverse: *«Согласовать слияние с владельцем — CLAUDE.md рабочий протокол»* написано как комментарий рядом с командами, но не выделено как отдельная стоп-точка с ожиданием ответа. [CONFIRMED — комментарий есть, явного СТОП/подтверждения нет]

### 6. `synthesize_and_save` может не пробросить `author_refs` — [LIKELY]

Шаг 1 говорит: *«Убедиться, что `author_refs` из `synthesize` остаётся в возвращаемом dict (не теряется)»* — но не даёт конкретного кода изменения `synthesize_and_save`. Агент должен «убедиться» сам. Если `synthesize_and_save` делает `return {**synthesize_result, 'artifact_id': aid}` — `author_refs` останется. Если он явно строит новый dict с известными полями — `author_refs` потеряется. Критерий готовности для этого шага: `build_digest` выводит `[Имя]` вместо `[@N]` — что обнаружит потерю, но только на финальном прогоне. Нет промежуточного теста на `synthesize_and_save` конкретно. [LIKELY — шаг описан как «убедиться» без кода; риск молчаливой потери поля]

---

### 7. Контракт `[#id]` в `_select_fragments` (Pass 1) — конфликт с новым `[@N]` — [CONFIRMED]

PLAN.md (решение 9): *«Pass 1 не трогаем по сути: отбор ДО группировки»*. Pass 1 (`_select_fragments`) строит вход с `[#id]` и просит LLM выбрать `[#id]`. После отбора группируем `selected` по автору в Pass 2. Шаги 1-2 меняют только Pass 2 и промпт Pass 2. **Промпт Pass 1 (`_select_fragments`) содержит инструкции про `[#id]`** — его план явно НЕ трогает. При >150 фрагментов оба прогона работают: Pass 1 отбирает по `[#id]`, Pass 2 синтезирует по `[@N]`. Два разных контракта в одном файле `digest_synthesis.md` — или Pass 1 использует отдельный промпт? Если один файл — промпт после переписи шага 2 сломает Pass 1 (нет `[#id]`-инструкций). [CONFIRMED — PLAN.md явно запрещает трогать Pass 1, но шаг 2 переписывает файл промпта без упоминания этой границы]

## Мелочи ([THEORETICAL] — низкий приоритет)

### T1. LLM игнорирует `[@N]` полностью — не использует ни одной ссылки

[THEORETICAL] При temperature=0.4 LLM может написать связный текст без ссылок (`[@N]`). `humanize_author_refs` не найдёт ничего для замены, в выводе не будет имён. Промпт это запрещает, но не гарантирует. Нет теста «в выводе есть хотя бы одна замена `[@N]`». Критерий «имена не дублируются» будет формально выполнен (имён нет вообще).

### T2. Один автор — вся группировка вырождается в один `[@1]` блок

[THEORETICAL] Если в периоде только один автор — все строки в «КТО ЧТО» будут `[@1]`. Работает корректно по логике, выглядит странно. Тесты этого не проверяют, но это не баг.

### T3. Ключ аноним `('anon', f['id'])` — `f['id']` это DB-id фрагмента или external_id?

[THEORETICAL] В `get_fragments_for_digest` возвращается `id` — предположительно DB integer. Если несколько анонимных сообщений от одного реального человека (нет sender_id, нет author_name) — они не объединятся. Это задокументировано в решении 2 плана как принятое поведение.

## Не найдено проблем

- Необратимые операции (DROP/TRUNCATE/DELETE/UPDATE SET NULL): **отсутствуют** во всех шагах.
- PII-утечка через `grouped_text` в LLM: механика `[@N]` без имён **верна**; тест `assert name not in text` предусмотрен.
- Трата OpenAI без предупреждения: шаг 3 явно маркирует smoke-прогон как **«СТОП-ТОЧКА: трата OpenAI»**.
- Сломанный scheduler: `build_digest` контракт `{text, found, used}` явно защищён в progress.md и step_1.
- Realtime-ingest: шаг 3 проверяет dup=0 после деплоя.
- OpenClaw/Hermes: шаг 3 явно упоминает «не затронуты».
