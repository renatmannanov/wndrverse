### Формат кейса (cases/*.json)
```json
{
  "name": "questions_to_women_2026-05",
  "topic": "questions_to_women",
  "since": "2026-05-01",
  "till":  "2026-05-31"
}
```
`since`/`till` — YYYY-MM-DD (или `null` для открытой границы). Раннер переводит
их в (since, until) через `parse_date_range` (until EXCLUSIVE) — тот же путь, что
`/summary`. Если обе границы null → передать since=None, until=None (весь корпус).

Точные импорты раннера (обе функции — модульного уровня в delivery/cli.py,
публичны, уже импортируются ботом):
```python
from delivery.cli import build_digest, parse_date_range
```

### Как выбрать кейсы (ОДИН путь — не «уточнить у пользователя»)
Раннер/исполнитель НЕ придумывает даты. Алгоритм формирования стартовых кейсов
(выполнить РАЗОВО при создании шага, руками, против локальной БД):
```bash
# 1. какие топики реально имеют данные (с числом сообщений, порог 80 уже из шага 3):
python -c "from core.store.fragments_db import get_topics_with_counts; \
from core.brain.synthesis import TOPIC_HINTS; \
[print(t, c) for t, c in get_topics_with_counts(only=set(TOPIC_HINTS))]"
# 2. взять 2–3 топика с наибольшим count.
# 3. для каждого — УЗКИЙ период (один календарный месяц), где есть сообщения.
#    НЕ использовать null/null (весь корпус) — это дорого по OpenAI на каждом прогоне.
#    Если не уверен в датах конкретного топика — взять последний полный месяц,
#    где count в этом топике > 10 (проверить get_fragments_for_digest на месяце).
```
Записать получившиеся `{name, topic, since, till}` в `cases/*.json`. Имя файла =
`<topic>_<YYYY-MM>.json`. Никаких `null/null`-кейсов в стартовом наборе.

### Раннер tests/golden/run.py (запуск: `python -m tests.golden.run`)
Поведение:
1. Грузит `.env` (DATABASE_URL/OPENAI_API_KEY) как delivery.cli.
2. Для каждого кейса: вызывает `build_digest(topic, since, until)`.
3. Пишет `result['text']` в `snapshots/<name>.txt` (перезапись).
4. Печатает в stdout краткую сводку: имя кейса, found/used, длина текста,
   и есть ли `critic_issues` (если build_digest их прокинет — опционально).
5. Сравнение со «старым» снапшотом — через git: раннер просто перезаписывает
   файлы, дальше `git diff tests/golden/snapshots/` показывает изменения.
   Раннер НЕ выносит вердикт (snapshot-режим, human-in-the-loop).

Флаги раннера:
- без аргументов → прогнать все кейсы из `cases/`, писать в `<name>.txt`.
- `--case <name>` → только один кейс.
- `--baseline` → писать в `<name>.baseline.txt` вместо `<name>.txt` (снимок
  ТЕКУЩЕГО кода ДО правок, для сравнения эффекта плана; тоже в .gitignore).
- `--check` → НЕ перезаписывать снапшоты; вместо этого сравнить новый вывод с
  существующим снапшотом и напечатать, для каких кейсов есть расхождение (exit
  code 1 если есть расхождения — для будущего CI). Без снапшота → «нет эталона,
  запусти без --check».

Один путь поведения для каждого режима — никаких «либо/или» в коде.

### PII / git — СТРОГИЙ ПОРЯДОК (иначе имена утекут в историю git)
`snapshots/*.txt` И `snapshots/*.baseline.txt` содержат РЕАЛЬНЫЕ имена (humanized
вывод) → это PII. Порядок действий ОБЯЗАТЕЛЬНО такой, без перестановок:
1. СНАЧАЛА добавить `tests/golden/snapshots/` в `.gitignore` (вся папка — и
   `.txt`, и `.baseline.txt`).
2. Проверить, что игнор работает: создать пустой `tests/golden/snapshots/.keep`
   нельзя (он попадёт в git) — вместо этого убедиться `git check-ignore
   tests/golden/snapshots/x.txt` печатает путь.
3. ТОЛЬКО ПОТОМ первый прогон раннера (создаёт снапшоты).
4. НЕ делать `git add -A` / `git commit` между шагами 1 и 3. Перед любым коммитом
   проверить `git status` — снапшотов в нём быть НЕ должно.
- В git идут только `cases/*.json` (topic+даты, не PII) и `run.py`.
- README-строкой в начале run.py пояснить: снапшоты локальные, не в git, содержат PII.
- cases/*.json не содержат PII (только topic + даты) — проверить перед коммитом.
