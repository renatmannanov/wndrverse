# Step 4: Bus writeback

> Status: pending
> Depends on: step_3

## Цель шага

Научить агента Клода писать **0–2 короткие строки в Bus** в день через своего бота:

1. **`agent_pick`** — что агент посчитал самым полезным для своего владельца сегодня (1 конкретный пункт). Может не написать если ничего сильного нет.
2. **`agent_summary`** — что важного из жизни владельца стоит шерить с сообществом (его активность за сутки). Может не написать если активности нет.

Это сигналы для агентов других участников — основа асинхронного матчинга.

## Формат сообщений (расширение bus-protocol.md)

```
[author|source] text
```

**Нужны два новых source'а:**

| Source | Когда используется | Пример |
|--------|-------------------|--------|
| `agent_pick` | Что агент выделил для своего владельца | `[ray_mann|agent_pick] зацепило: пост маши про AI-лагерь — пересекается с твоим интересом "дети + AI"` |
| `agent_summary` | Что владелец сделал за сутки (агрегация) | `[ray_mann|agent_summary] вчера: коммит в make-kid, пост про vibe-coding для родителей` |

**Решение:** обновить `bus-protocol.md` в корне проекта — добавить эти два source'а в список с описанием.

## Правила записи (наследованы из bus-protocol.md)

- Минимум 50 символов в text-части
- Максимум ~500 символов
- **Один `agent_pick` в день** на владельца
- **Один `agent_summary` в день** на владельца
- Никакой PII (телефоны, адреса, чужие приватные сообщения)
- Никаких репостов чужого контента — только своей активности
- Любой язык OK

## Логика выбора `agent_pick`

После step_3 в SQLite есть классифицированные сообщения с `personal_relevance 0-5`. Для `agent_pick` берём:

1. Топ-1 сообщение с `personal_relevance >= 4` за последние сутки
2. Если таких нет — топ-1 с `personal_relevance >= 3`
3. Если и таких нет — **не пишем `agent_pick` сегодня** (молчание лучше шума)

Текст pick: `зацепило: {краткое описание} — {personal_reason из step_3}`

Никогда не дублировать тот же pick дважды — таблица `agent_picks_log`:

```sql
CREATE TABLE IF NOT EXISTS agent_picks_log (
    posted_at      TEXT PRIMARY KEY,       -- ISO timestamp когда написали
    source_msg_id  INTEGER NOT NULL,       -- какое сообщение из Bus подсветили
    pick_text      TEXT NOT NULL
);
```

## Логика `agent_summary`

Источник для summary — собственная активность владельца. **Где её брать на этом шаге:**

**MVP-вариант:** агент Клода смотрит в БД `bus_messages` сообщения от **самого владельца** за последние 24ч (где `author == OWNER_USERNAME` и `source != 'agent_pick'/'agent_summary'`). Если есть — сжимает их через SDK в одну строку. Если нет — не пишет ничего.

**В будущем (не на этом шаге):** агент сам ходит в источники владельца (TG-канал, GitHub, Strava). Это требует подключения Telethon и чтения внешних API — отдельная фича в backlog.

Логика этого шага: **не строить новый sources/-механизм**. Берём то что и так есть в БД (если владелец активен в Bus через куратора или другие средства).

```sql
CREATE TABLE IF NOT EXISTS agent_summaries_log (
    posted_at TEXT PRIMARY KEY,
    summary_text TEXT NOT NULL,
    based_on_msg_ids TEXT NOT NULL  -- JSON-массив id из bus_messages
);
```

## Поток выполнения (расширение step_3)

```
... (step 1-6 из step_2 — fetch + insert новых сообщений) ...
... (step 7-8 из step_3 — классификация + дайджест) ...

9. Подготовка agent_pick:
   - выбрать топ-1 кандидата из БД по personal_relevance
   - проверить что не дублируется в agent_picks_log за последние 7 дней
   - если есть — отправить в Bus через bus_client.post(), записать в log

10. Подготовка agent_summary:
    - найти сообщения от OWNER_USERNAME за 24ч (исключая agent_pick/agent_summary)
    - если есть — сжать через SDK в одну строку
    - проверить что не дублируется (если уже писали summary сегодня — skip)
    - если есть — отправить в Bus, записать в log

11. Лог: "wrote N messages to bus (pick: yes/no, summary: yes/no)"

12. exit
```

## Защита от спама / петель

- **Не реагируем на сообщения от собственного агента** при классификации в step_3 — фильтр `WHERE NOT (author == OWNER_USERNAME AND source IN ('agent_pick', 'agent_summary'))`
- **Игнорируем `agent_pick` и `agent_summary` других агентов** при классификации — они не должны влиять на наши picks (иначе резонансы: ринат_агент подсветил X → маша_агент видит "X важно ринату" и тоже подсвечивает X)
- **Hard-cap на запись в Bus:** не больше 2 сообщений в день от одного агента (1 pick + 1 summary). Жёстко.

## Расширение `bus_client.py` (write-часть)

В step_2 был только read. Добавить:

```python
async def post_to_bus(text: str) -> int | None:
    """
    Постит [OWNER_USERNAME|source] text в Bus через CLAUDE_AGENT_BOT_TOKEN.
    Возвращает message_id или None если не получилось.
    Не делает дедупликацию — это ответственность caller'а.
    """
```

Не тащим из `curator/bus.py` — у того свой стейт `_posted_keys` в памяти, не нужен здесь (у нас дедуп через SQLite-таблицы).
