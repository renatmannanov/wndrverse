## Идентификация участников

**Primary key — Telegram ID**, не username. Username меняется, ID — никогда.

```json
{
  "tg_id": 123456789,
  "tg_username": "vasya_petrov",
  "github": "vasya-petrov",
  "strava": "12345678"
}
```

**Онбординг через бота:** человек пишет `/start` агенту → бот автоматически получает tg_id. Никакого ручного ввода. Связка с GitHub — на доверии в MVP (человек указал сам).

## Двухуровневая память

### Память куратора (org-репо: `wndrverse/curator`)

```
curator/
├── members.json              ← поверхность: кто участник, короткое био, интересы, линки
├── profiles/
│   ├── vasya.json            ← что куратор узнал о Васе в процессе (накапливается)
│   └── masha.json
└── matches/
    └── 2026-04.json          ← история мэтчингов
```

**`members.json`** — публичный конфиг, обновляется через PR. Версионируется.

**`profiles/*.json`** — динамический слой. Куратор пишет сюда по мере того как участник появляется в шине. Не все сразу — по мере циркулирования контента.

**`matches/*.json`** — кто с кем, по какой теме, когда. Используется чтобы не повторять мэтчи и видеть историю связей.

---

### Память участника (личный репо: `vasya/wndr-agent`)

```
memory/
├── me.json                   ← кто я, линки, интересы, над чем работаю
└── encounters/
    ├── masha.json            ← детали о Маше с моей точки зрения
    └── petya.json
```

**`me.json`** — куратор читает это как источник профиля. Человек и агент обновляют совместно.

**`encounters/*.json`** — личная разведка агента. Может появиться:
- после мэтча с участником
- без мэтча: агент уловил что-то интересное из поста в шине и записал себе

Куратор **не пишет** в чужие репо. Он только читает `me.json` и при необходимости берёт детали из `encounters/`.

---

## Принцип обмена памятью

**Никто не мержит данные к себе автоматически.** Каждый хранит у себя, при необходимости читает у других.

```
Агент Васи          GitHub (личный репо)        Куратор
    │                       │                       │
    ├── читает шину          │                       │
    ├── видит пост Маши      │                       │
    ├── записывает деталь ──▶│                       │
    │   encounters/masha     │                       │
    │                        │◀── читает me.json ────┤
    │                        │◀── читает encounters/ ┤ (если нужно для мэтча)
    │                        │                       │
    │◀── читает profiles/ ───┤                       │
    │    (что куратор знает) │                       │
```

**Детали из `encounters/` не попадают к куратору автоматически.** Куратор берёт их только если считает полезным для конкретного мэтча.

## Ротация по неактивным участникам

Без явного механизма куратор знает 10 активных и не знает 90 остальных.

**Решение:** `last_observed_at` в профиле каждого участника.

```json
{
  "tg_id": 123456789,
  "last_observed_at": "2026-03-01",
  "signal_strength": 0.3
}
```

- Раз в неделю куратор принудительно берёт в работу тех, кто давно не всплывал
- Если контента нет совсем → бот пишет участнику в личку: "как дела? что делаешь?" + просит прокомментировать пост кого-то из сообщества
- Это одновременно и сбор данных, и активация участника

## Онбординг-флоу

При первом запуске агент не постит в шину — сначала собирает профиль.

```
новый участник
    │
    ▼
пишет /start агенту
    │
    ├── агент тянет интро из WNDR-группы (если есть)
    ├── задаёт 3 вопроса в личку:
    │     1. Над чем работаешь прямо сейчас? (одно предложение)
    │     2. Что хочешь найти в сообществе?
    │     3. Какие темы точно не интересны?
    │
    ├── генерирует me.json
    ├── показывает превью владельцу → "всё верно?"
    │
    ▼
git push → memory/me.json
    │
    ▼
куратор подхватывает при следующем цикле
```

**Интро из WNDR-группы** — ценный источник: люди там уже постарались. Агент парсит интро, извлекает структуру, просит дополнить только пробелы.

**Consent:** форк шаблона = согласие с правилами. Явно прописать в README шаблона.

## Обновление профиля

Данные устаревают. Двойной механизм:

- **Агент:** раз в месяц спрашивает владельца в личку "это всё ещё актуально?"
- **Человек:** может обновить `me.json` вручную в любой момент → git push → куратор подхватит

## Холодный старт

Первые недели шина пустая → витрина молчит → люди отписываются.

**Решение:** контент из живой WNDR-группы.

- Telethon (userbot) читает историю группы
- Куратор берёт посты с наибольшим числом реакций за последние N недель
- Этот контент идёт в витрину на старте
- Параллельно — материал для первичного профилирования участников

> Технически: реакции в Telegram читаются через Telethon, но нужен userbot, не бот-токен.

```

│   ├── members.json
│   ├── profiles/

| Кто | Куда пишет | Куда не пишет |

## Эволюция хранилища

```
MVP          →   v2              →   v3
JSON файлы       Markdown файлы      Obsidian vault / Notion API
в GitHub         (читабельны как     как альтернативный бэкенд
                 личный дневник)     по желанию участника

Markdown как промежуточный шаг интересен: тот же git, но человек может открыть свой репо в Obsidian и читать память агента как личный дневник.

## Верификация GitHub-аккаунта

Два варианта, от простого к надёжному:

**MVP — доверие:** при онбординге бот спрашивает "дай ссылку на GitHub профиль". Человек указал сам. Подделать можно, но в закрытом сообществе смысла нет.

**v1.5 — Gist-верификация** (без OAuth, без приложений):
```
1. Бот говорит: "Создай публичный Gist с текстом: wndrverse-verify-123456789"
2. Человек создаёт gist, даёт ссылку
3. Бот проверяет через GitHub API что gist существует и текст совпадает
4. Связка подтверждена
```
Работает как domain verification у Google. Один раз, навсегда.

**v2 — GitHub OAuth:** полноценно, но требует OAuth App. Для 100 человек избыточно.

## Куратор как Telegram-бот

Куратор — это Telegram-бот. Все коммуникации с участниками идут через `bot.send_message(tg_id, ...)`.

Именно поэтому **tg_id как primary key критичен** — без него невозможно написать конкретному человеку в личку.

Куратор пишет участникам в трёх случаях:
- онбординг нового участника
- найден мэтч → личное уведомление обоим
- участник давно неактивен → мягкое касание

## Нетехнические участники (большинство)

Большинство участников не будут форкать шаблон и запускать агентов. Для них система должна работать **пассивно и незаметно**.

### Онбординг без кода

Куратор сам их находит и онбордит:

```
1. Куратор читает WNDR-группу (топик с интро)
2. Парсит интро, строит черновик профиля
3. Пишет в личку:
   "Привет, я WNDRverse. Вижу ты занимаешься [X].
    Буду следить за твоим каналом и шарить интересное.
    Вот как я тебя понял — всё верно? [превью профиля]"
4. Человек отвечает да / поправляет
```

Никакого GitHub. Никакого форка. Ответил в Telegram — ты в системе.

### Что они получают (польза без усилий)

- Видят себя в витрине — куратор процитировал их пост
- Получают личное сообщение "тебя и Машу интересует одно — познакомить?"
- Их старый пост всплывает перед нужным человеком в нужный момент

Это невозможно в обычной группе где всё тонет. Ты существуешь для сообщества даже когда молчишь.

### Как подтягивать в процессе

Куратор периодически пишет неактивным — не абстрактное "как дела?", а с контекстом:

> "Давно не виделись. Маша написала про детское обучение — мне кажется тебе откликнется. Что думаешь?"

Это одновременно мягкий мэтч и активация. Без публичного поста в витрину.

## Ценность системы

Три разные пользы для разных участников:

**Нетехник:** ты существуешь для сообщества даже когда молчишь. Старый пост всплывает перед нужным человеком.

**Активный участник:** контент находит конкретных людей которым он релевантен, а не размазывается по 100 подпискам.

**Вайбкодер:** реальный полигон. Живые данные, живые люди, не демо-проект.

**Общая польза:** слабые связи которые иначе не случились бы. Социологи называют это *bridging capital* — самый ценный тип социального капитала, и самый хрупкий в больших группах. WNDRverse его механизирует.

## Добавление куратора как collaborator (автоматизация)

При онбординге участник даёт github username → бот делает одну API-команду:

```
PUT /repos/{owner}/wndr-agent/collaborators/wndrverse-curator
{ "permission": "pull" }
```

Участник получает email от GitHub → принимает приглашение. Репо остаётся личным, доступ минимальный (только read).
